security/compliance; spec-conformance/operability), each given the six defect *classes* already
known here as a prior rather than a list of instances. Findings below are deduplicated and
renumbered `A1…A31`, ordered by severity.

audit that reported it. `REPORTED` — an audit confirmed it with quoted evidence and I have not

## The cross-cutting diagnosis

**Ten of the thirteen security findings are inversions of a control that already exists
elsewhere in this repo.** Not an absence of standards — a guard invented at one site and never
lifted into the shared seam that all ten plugins already call:

| The guard exists here | …and is missing here |
|---|---|
| `verify_minter_capability` is a `*bool`, so an old config cannot silently lose the check | `flush_interval` / `reconcile_cadence` have no guard at all (A2) |
| `retireGrace()` checks `> 0` and falls back (`minter_retire.go:56`) | `worker.Register` accepts a non-positive interval (A2) |
| `issuanceError` deliberately withholds the upstream body | `capability.Gate.run` returns it to the caller (A4) |
| The retired-**minter** sweep logs every deletion | The **orphan** reconciler logs none (A6) |
| Five cloud listers propagate delete errors | Azure swallows them and reports success (A8) |
| The DO recorder redacts UUIDs | The AWS recorder does not — three real request IDs are committed (A21) |
| `forbidigo` bans `logical.ErrorResponse` | Nothing bans a bare `return nil, err` (A7) |
| AWS enforces a 2-key quota guard before minting | No other quota is checked anywhere |
| `metrics/entity/<id>` path segments are `url.PathEscape`d | `rotation_params` values are interpolated raw into upstream URLs (A20) |
| Nine clients set a 30s HTTP timeout | AWS STS sets none (A19) |

This also explains why the conformance table did not catch them: it enforces that categories
**exist**, not that the assertions inside them are **reachable** (A9, A10, A11).

**The structural remedy**, which should shape every fix below: when a guard is added, add it to
the `pkg/` seam all ten call, not to the plugin where the bug was found.

## Critical

### A1 — **[FIXED 42939dc]** The orphan reconciler deletes the minter credential that rotation just created · VERIFIED · UpCloud + Akamai live, Azure conditional, Exoscale masked

Rotation names the successor into the namespace the reconciler reclaims
(`plugins/credential-upcloud/upcloud_client.go:30,190` — `successorTokenNamePrefix =
"cloud-creds-minter-"`; same shape `credential-akamai/akamai_client.go:290`,
`credential-azure/azure_client.go:272`, `credential-exoscale/consts.go:47`). The reclaim filter
is that bare prefix (`reconciler_integration.go:12,26`), and the known-set is **issuance-only** —
`active-tokens/` is written at `path_creds.go:108` (issue) and deleted at `:153,:174` (revoke),
never for a successor, whose upstream ID lands in `RotationParams`.

So a documented `minter-sets/<name>/rotate` is followed, within one reconcile pass past the 1h
hold, by the plugin deleting its own new mint-capable credential upstream — plausibly
authenticating that delete with the credential it is destroying (`anyHealthyMinter`). The
predecessor is already `Retired` and skipped by `selectMinter`, so the set ends with no usable
minter and the cloud stops issuing, rotating and revoking. Silent (A6). UpCloud/Akamai populate
`CreatedAt` so the age guard expires; Exoscale is spared only by A5.

The comment on that constant states the mechanism as if it were protection: *"the owner-tag
prefix the reconciler recognises"*. It is the delete trigger.

**Fix:** register minter/successor upstream IDs in the known-set (preferred — keeps one
reclamation rule), or exclude the minter prefix in `pkg/reconciler`. Plus the conformance case
that does not exist: **a rotation successor must survive a reconcile pass.**

### A2 — **[FIXED 42939dc]** A persisted non-positive interval crash-loops the plugin process · VERIFIED · all 10

`pkg/worker/worker.go:96` builds the ticker in `run`, outside the `recover` that wraps only
`w.fn` (`:111-118`). `time.NewTicker(0)` panics in a bare goroutine. `framework.TypeDurationSecond`
rejects negatives but accepts an explicit `0`, and a schema `Default` applies only when the key is
absent; no plugin bounds it. The config is `Put` **before** `go b.startWorkers(...)`, and
`Initialize` re-runs `startWorkers` on every mount/unseal/reload — so the poison is durable and
raft-replicated. All ten use `ServeMultiplex`, so **every mount in the binary** dies, not only the
misconfigured one. Reproduced: `panic: non-positive interval for NewTicker`.

**Fix:** validate at role/config write **and** clamp defensively in `worker.Register` (the seam),
per the diagnosis above.

### A3 — **[FIXED 99ab6b7]** Unvalidated endpoint overrides exfiltrate every minter credential · VERIFIED · 8 plugins + GCP equivalent

`api_url` / `sts_endpoint` / `graph_endpoint` / `login_endpoint` / … are persisted, rehydrated and
used in production, described as "(for testing)". **No plugin validates scheme or host** — no
`url.Parse`, no allowlist, in any `path_config.go`. The minter token is then sent to whatever host
is named: `req.Header.Set("Authorization", "Bearer "+c.token)` against `c.baseURL`
(`plugins/credential-do/do_client.go:66-71`).

Config-write privilege — strictly less than reading a minter secret, which no endpoint exposes —
becomes exfiltration of every minter in every set within one health-check interval, in plaintext
if `http://` is chosen. GCP has no override field but takes `token_uri` verbatim from
operator-supplied SA JSON (`iam_client.go:112-115`) and POSTs a signed JWT to it, returning the
response body in the error as an oracle.

Aggravators: `CheckRedirect` is nil on all ten clients (default 10-redirect follow), and there is
no `io.LimitReader` anywhere against 39 unbounded `resp.Body` reads.

**Fix:** see **D2** — constrained by the test architecture, which points these fields at
`http://127.0.0.1:PORT`.

## High

### A4 — **[FIXED 1997df3]** Raw upstream bodies are returned to API callers on every configuration path · VERIFIED · all 10

`README.md:22` and `SUMMARY.md:41` claim, unqualified: *"Raw upstream response bodies are logged
operator-side, never returned to clients."* `pkg/capability/gate.go:93-98` both logs **and**
returns the same error, and the `%w` chain is unbroken to
`fmt.Errorf("DO API returned %d: %s", status, body)`. Reachable from `minter-sets/<name>`,
`roles/<name>` and `rotate` on all ten; the same shape recurs at `path_reconcile.go:70` in nine
plugins and at seven rotation sites.

A caller with only `create` on `roles/*` receives verbatim cloud diagnostics — Azure `AADSTS`
codes with tenant/correlation/trace IDs, Graph object IDs, GCP project and SA detail. It defeats
the fixed `"upstream credential issuance failed"` string on the read path, since a role write
probes the same minter with the same mint shape. The repo already knew:
`real_cloud_record_test.go:289-291` says *"a 4xx body can quote the request"*.

**Fix:** classify and summarise in the gate (status + code, not body); log the body only. Add the
missing invariant test — there is none (`rg -i 'upstream body|leak' pkg/plugintest/` is empty).

### A5 — **[FIXED f437719]** Exoscale and Vultr orphans can never be reclaimed, and KI-004's documented workaround no longer works · VERIFIED · 2 plugins

`pkg/reconciler/reconciler.go:109-113` skips any entity whose age is unconfirmable when
`ConfirmationHold > 0`. Neither lister sets `CreatedAt` (their APIs expose none). The **manual**
endpoint clamps the request *upward* to `MinConfirmationHold` (5m) —
`plugins/credential-exoscale/path_reconcile.go:42-46` — so `confirmation_hold=0` no longer reaches
`Run`. KI-004 and `ttl-semantics.md:88-90` both prescribe exactly that as the remedy.

These are hard-revoke clouds whose credentials have **no upstream expiry**, so this is a permanent
leak with no code path to fix it, reported to the operator as `"orphans_found": 0`. A Vultr orphan
is a standing sub-user account with ACLs. KI-004's *"it's not a security hole"* no longer holds.

**Fix:** see **D3** — trades the fail-closed age guard against reclaimability.

### A6 — **[FIXED abef9b0]** Reconciler deletions are unlogged, unmetered, unauditable and unstoppable · VERIFIED · all 10

Four gaps compose: `pkg/reconciler` has **no logger at all**; the six deleting plugins **discard
the whole `Result`** (`workers.go:105` `_, err = …Run(...)`), dropping `orphans_found`, `HitLimit`
and per-entity `Errors`; the pass is timer-driven so **no OpenBao request exists and no audit
device can record it**; and `emitOrphansFound` is called only from the *manual* handler on those
six — the four clouds that delete nothing are the ones that meter it.

Refuted documentation: `techrfc.md:131` "audit logging" among the safeguards; `design.md:297`
"every auto-delete writes a structured log line and emits `cloud_creds_auto_deleted_total`" (zero
occurrences); `techrfc.md:131` per-role `disable_auto_delete` — declared at
`pkg/cloudconfig/role.go:13`, read by nothing, on no schema, and unimplementable as specified
because `reconciler.Run` has no role concept; `design.md:285` orphans "marked `state=missing`,
alarmed" — `RecordMissing()` has zero callers.

"What did the reconciler delete, and when" is unanswerable from any source, and a real pass is
indistinguishable from a `dry_run`.

### A7 — **[FIXED 4c1a040]** API-002 is broken again at 229 sites, through a door the lint does not watch · VERIFIED · all 10

`forbidigo` correctly bans `logical.ErrorResponse` outside `pkg/credenvelope`. But handlers also
return a bare Go error, which core renders as a **code-less 500**: **229** `return nil, err` in
`plugins/*/path_*.go`. Reachable from any storage failure — raft quorum loss, a corrupt entry
hitting `json.Unmarshal`. Same defect as the 166 code-less responses fixed on 2026-08-22, larger,
via a different mechanism.

`framework.Backend.HandleRequest` also emits `logical.ErrorResponse("Field validation failed: …")`
before plugin code runs, so any mistyped field yields a response with no code.

### A8 — **[FIXED 1997df3]** Azure reports every reconciler deletion as successful whether or not it happened · VERIFIED · 1 plugin

`plugins/credential-azure/reconciler_integration.go:41-53` loops the known app object IDs,
returns `nil` on first success, and **returns `nil` after every attempt failed**. So
`result.Deleted` increments and `result.Errors` stays empty even when every Graph call failed on
auth, throttling or 5xx: a false positive record of a security-relevant deletion, with live client

Same file is a fan-out amplifier: one reconcile is `A + 10A` Graph calls, conceded in a comment.

`pkg/plugintest/reload.go:51-66` asserts only that `Initialize` returns nil twice and that

### A12 — **[FIXED abef9b0]** Every metric goes to a blackhole in the shipped deployment · VERIFIED · all 10

`pkg/telemetry` emits through go-metrics' package-level globals
(`metrics.SetGaugeWithLabels`/`IncrCounterWithLabels`), whose default sink is `BlackholeSink`
until `NewGlobal` is called. **Nothing in this repo installs a sink outside `_test.go`.** The
plugins are separate OS processes registered externally, so the operator's `telemetry` stanza
configures *core's* registry, not theirs; `logical.BackendConfig` carries no sink and
`sdk/v2/plugin/` has zero go-metrics references.

So `cloud_creds_minter_age_seconds`, `upstream_state`, the lease counters — all discarded, and
every alert threshold in `design.md` is unbuildable. Every observability test installs its own
sink first, which is precisely why the call sites are proven and the missing sink is invisible.

**Fix:** see **D1** — may not be solvable in-process.

### A13 — **[FIXED f437719]** A minter-set write silently un-retires rotated-out minters and cancels the sweep · REPORTED · 6 rotation clouds

`parseMinters` reads only `id`, `token`, `never_expires`, `expires_at`, `rotation_params` — never
`retired`/`retired_at` — and `pathMinterSetWrite` persists the set wholesale with no merge. So any
write during the 7-day grace resets `Retired=false`, re-admitting a credential scheduled for
deletion to issuance **and** permanently cancelling `sweepSet` (keyed off `RetiredAt`), so the old
mint-capable upstream credential lives forever. It also re-stamps `CreatedAt: time.Now()` on every
minter, resetting the age gauge (all ten). Aggravated by there being no safe round-trip: retirement
is not observable through any read endpoint.

### A14 — **[FIXED f437719]** A mount that never had `config` written runs zero workers, and one auth blip then wedges a minter forever · REPORTED · all 10

`startWorkers` returns early when `b.config == nil`, and nothing else requires config:
minter-set and role writes succeed, endpoints default, and the capability gate treats nil config as
verification-**enabled**. So `minter-set → role → read` issues credentials with no health check, no
metrics flush, no reconciler and no retired-sweep. The **only** exit from `AuthFailing` is a
successful health check, and only a worker runs those — so one transient blip withdraws a minter
permanently, from issuance, revoke, rotation and reconcile alike.

### A15 — **[FIXED adca1be]** `credential-oci`'s production client is four `NotImplemented` stubs while three status documents say otherwise · VERIFIED · 1 plugin

`plugins/credential-oci/oci_client.go:51-69` — `CreateAuthToken`, `DeleteAuthToken`,
`ListAuthTokens`, `GetUser` each return `ErrUnsupported` / 501, and `backend.go:160` wires that
client in production. `CLAUDE.md:36`, `SUMMARY.md:9` and `README.md:5` all state "None are

### A19 — **[PARTLY FIXED a3ff4d7+]** Two mounts against one cloud account delete each other's live credentials · REPORTED · 6 plugins

The reclaim filter is the global `cloud-creds-` prefix with no mount, namespace or cluster
component, and the known-set is a per-mount `active-tokens/` view. Two mounts, or prod and
staging, or two clusters against one account, each see the other's live credentials as orphans and
delete up to 10 per pass, silently. `docs/decisions.md:77` actively recommends multiple mounts as
an isolation strategy with no warning. `CLAUDE.md:91` claims the scheme is `cloud-creds-<role>-`;
the matching side uses only `cloud-creds-`. Same root cause as A1: the tag identifies the product,
not the instance.

**Fix:** D5 chose a new scheme with a one-time migration. `pkg/ownertag` now implements it —
a per-mount instance id minted on first use and persisted (nothing in the plugin API gives a
timer-driven worker a durable mount identity), with `Owns` deliberately refusing a name that
carries the base prefix but a different instance id. The property is proven by a unit test:
two mounts do not own each other's credentials, the id survives a reload, and a
pre-migration name is **not** claimed — so old credentials become unmanaged rather than
deleted, which is the safe direction.

**Still to do: the wiring.** Seven credential-naming sites, six reclaim filters and
`capability.ProbeName` must move onto it, and the instance id must be threaded to mint,
reconcile and probe time. Staged separately on purpose: this is the one change in the audit
where a mistake deletes a customer's live credentials, the nets that would catch it are the
reconciler-safety category and the new unit test, and it deserves its own reviewable commit
rather than being appended to a long session. Until it lands, `decisions.md` no longer
suggests multiple mounts as an isolation strategy and states the constraint instead.

**Migration, when it lands:** credentials named `cloud-creds-<role>-<id>` stop matching the
new filter, so they survive as unmanaged and need manual cleanup once their leases expire.
Matching both shapes for a release was rejected — it would preserve exactly the cross-mount
deletion the change exists to stop.

No artifact provenance at all: `make build` produces no artifact, no `-trimpath`/`-ldflags`/
`-buildvcs`, no release target, no SBOM, no signing, and **README has no installation section** —

### A22 — **[FIXED adca1be]** AWS credentials carry the target role's full permissions; the two documented narrowing fields do not exist · VERIFIED · 1 plugin

`techrfc.md:208` and `design.md:107` specify `policy_arns[]` and `inline_policy`. Neither exists;

### A23 — **[OPEN]** Access metrics answer a different question than documented, and renewals were never counted · REPORTED · all 10

`decisions.md:21-31` argues at length that the key **must** be the cloud entity. It is
`"<minter_set>/<minter_id>"` on all ten, so "when was this IAM role last handed out?" — the
endpoint's purpose — cannot be asked. `RecordAccess` has exactly ten call sites, all in
`pathCredsRead`: **renewals are not counted**, so a long-lived renewing lease is indistinguishable

Storage layout differs from the spec (no `<cloud>` segment, `<role>` inserted, no `flush_seq`, no
7-day prune), `staleness_seconds` is always 0 on a single node, and `AccessCount` regresses on
restart.

### A24 — **[FIXED adca1be]** OCI: the envelope contradicts itself, and the documented rotated-slot grace does not exist · REPORTED · 1 plugin

`ttl_seconds` is clamped to `min(default_ttl, time-to-next-rotation)` while `expires_at` is
**not** clamped — with `default_ttl=15m` and 3 days to rotation the response says `900` and an
`expires_at` three days out. OBC-007(b) requires a 7-day grace from `retired_at` before deleting a
rotated-out slot credential; `rotateSlot` deletes it **inline**, the `slot` struct has no
`retired_at`, and `slotRetiring`/`slotRetired`/`slotEmpty` are declared and never assigned.
**SUSPECTED:** `maxSlotCount = defaultSlotCount = 2` against a 2-token-per-user cap, with the
replacement created before the incumbent is deleted — so rotation may need a third token and
cannot succeed at the default configuration.

### A25 — **[FIXED 8b29fe4]** Recovery state is in-memory only and is reset by ordinary operator actions · REPORTED · all 10

`loadMinterSet` constructs a **fresh** `StateMachine` per minter and is called from every
minter-set write, every rotation commit and every sweep that changes anything. So an `AuthFailing`
minter becomes `Healthy` and immediately selectable, and an open rate-limit cooldown is discarded,
on an unrelated write — making RSK-007's "operator never sees a sustained signal" strictly worse
than documented. Retired minters keep publishing `upstream_state{state="healthy"}` for the whole
grace, and `upstream_state` is emitted as `1` for the current state without zeroing the previous
label set, so `healthy` and `auth_failing` can both read 1.

### A26 — **[FIXED abef9b0]** Logs cannot diagnose the top three failure modes · REPORTED · all 10

`issuanceError` logs `cloud`, `status`, `error` and omits role, minter set, minter id and `req.ID`
— all four in scope at the call site. There is **no issuance-failure counter at all**. Revoke
failure omits credential ID, lease ID, minter and role, while the *less* important local-tracking
failure two lines later logs `token_id`. Nothing logs or emits the breaker at all, and a 429 is
laundered into `RecordError(503)` so it is indistinguishable from a 500. No state-transition
logging anywhere. Five plugins swallow health-check transport errors (`if err != nil { continue }`).
Spam: "minter nearing expiry" re-logs at `Warn` every tick — ~288 identical lines/day/minter for up
to seven days.

### A27 — **[FIXED 8b29fe4]** No health or readiness surface · REPORTED · all 10

`pathMinterSetRead` returns `{name, minter_count, minter_ids}` on all ten. Recovery state,
`last_success_at`, `consecutive_failures`, `expires_at`, `created_at`, `retired`/`retired_at` are
all in the same process and none is exposed; there is no `health` path. Combined with A12, an
operator has neither a metric nor an endpoint that answers "is this mount healthy?", and after a
rotation cannot see which minter is retired or when the sweep will act.

## Lower, but real

### A28 — **[OPEN]** Uniformity is skin-deep · REPORTED
The eleven path patterns, the rotate rejection, the `minter_set` requirement and the renewability
set are genuinely uniform. Behind them: `metadata.scope` means ten different things (a scope list,
an ACL list, an *identity*, or the literal `"all"`); `reconcile` has three response schemas;
`minters[]` takes five element shapes (`token`, `access_key_id`+`secret`, `credentials_json`,
`client_id`+`client_secret`, and gratuitously `key` on Exoscale); role-TTL defaults vary 400×; the
required cloud role field is validated on five clouds and unvalidated on five; `scopes` is a slice
on GCP and a string elsewhere; `minter_retire_grace` and `rotation_params` are settable and inert on
four. `credential` block: Azure's `subscription_id` is conditional, OVH contradicts the "frozen"
doc entirely, and the Exoscale/Vultr/Akamai/OCI schemas are documented nowhere — 40% of the
client-facing payload is unspecified and untested.

### A29 — **[PARTLY FIXED fe73636]** Smaller security and correctness items · REPORTED unless noted
- **Probe fan-out has no cooldown, cache or cap and bypasses the rate limiter entirely** — no
  `TryAcquire`/`RecordUpstream` in any of the ten `capability.go`, so a probe storm is neither
  gated by a cooldown nor able to open one. One minter-set write costs up to `2 × M × R'` real
  mints, uncached, so an idempotent Terraform re-apply re-mints every time. On OVH each probe
  leaves a live 1h token with **no revoke API**.
- **`mode` fails open**: `dryRun := mode == "dry_run"` on an unvalidated free string, so `dryrun`,
  `dry-run`, `DRY_RUN` all run a **live destructive pass** and the response then echoes
  `"dry_run": false`.
- **UpCloud's envelope misstates privilege**: `scopes` is declared, stored, echoed and placed in
  the envelope, and `createTokenRequest` has no scope field — the token carries account defaults.
- **GCP roles default to full `cloud-platform` scope**, the plugin's only privilege control there.
- **`credential_id` is an unsalted SHA-256 of the credential's own secret prefix** on GCP and OVH.
- **`rotation_params` values are interpolated raw into upstream URL paths** in the six rotation
  plugins; not one `url.PathEscape` in any plugin client. Worst on GCP, where `key_name` *is* the
  resource path.
- **`isNoSuchEntity` matches an upstream-controlled substring**, so a failed AWS key delete can be
  recorded as success, leaving a long-lived key alive with its tracking dropped.
- **AWS session names truncate from the tail**, so a role name ≥44 chars erases `req.ID` and every
  lease shares one `RoleSessionName`, destroying CloudTrail attribution.
- **AWS's STS client sets no HTTP timeout** — unbounded, reachable from the health worker whose
  context has no deadline, aggravated by A3.
- **Nil dereference in OCI `pathRotateSlot`** — `loadSlot` returns `(nil, nil)` when absent and
  `updated.TokenID` is read unchecked; a concurrent role delete panics the handler.
- **Three real AWS request IDs are committed** (`POST_AssumeRole_200.json`) — VERIFIED. The DO
  recorder has a `uuidShaped` rule; the AWS one has none. And `uuidShaped` is **absent from DO's own
  fail-closed gate**, which checks only known secrets, the PAT prefix and email — so a
  `DELETE /v2/tokens/<uuid>` recording would commit that UUID unchallenged. Same class as the email
  that got through once.
- **Duplicate minter IDs pass validation then collapse to one** (`states[m.ID] = …`, last wins),
  defeating RSK-005; there is no minter-ID validation at all, so an absent `id` yields the literal
  minter ID `"<nil>"`.
- **`ValidateMinterSet` is never called on load**, so a persisted invalid set is used fail-open,
  contradicting OBC-005's "hard config-load failure".
- **The 24h reconciler bootstrap delay is re-armed on every `startWorkers`** — including every
  minter-set write — so a write every 23h means the orphan backstop never runs.
- **Unpruned keyspaces**: `metrics/<entity>/<role>/<node>` grows permanently (entity embeds the
  minter ID, so every rotation adds keys); `MetricsStore` has no `Delete` and `AccessTracker` has
  no eviction, contradicting `design.md:329` and RSK-006's stated mitigation. `metrics/stale` is an
  uncapped O(N) recursive walk with one raft `Get` per leaf, on a request path.
- **`Cleanup` blocks a process-wide lock** — `wm.Wait()` waits for in-flight ticks (up to a 30s
  HTTP timeout) while the SDK holds its global instances lock, stalling unrelated mounts.
- **No leader/standby fencing**; and `decisions.md:120-131` justifies the 7-day retire grace with
  "other nodes keep the old minter in their in-memory snapshot" — a multi-node-live-backend model
  OSS does not have, so the grace protects against something that cannot happen while the failover
  window that can is unfenced.

### A30 — **[OPEN]** No storage schema version or migration story · REPORTED · all persisted entries
Nothing carries a version: minter sets, roles, config, `config_meta`, tracking entries, slots,
metrics, lease `internal_data`. Every mutation is read-struct/mutate/write-whole-struct, and
`encoding/json` drops unknown fields — so an older binary that touches a set **erases**
`Retired`/`RetiredAt`/`RotationParams`, reproducing A13 by version skew. Zero-value means
"dangerous" in at least two places (`CreatedAt` zero → age gauge reports ~2×10⁹; `MinterSet` empty
→ reported as `config_invalid` rather than a migration failure). Renaming a `framework.Secret.Type`
or an `internal_data` key would silently orphan every live lease. Related: a missing
`internal_data` field makes revoke **retry forever** in the six hard-revoke plugins — KI-002's
exact class, with the "minter gone" cause fixed and the "field absent" cause not.

### A31 — **[FIXED 4c1a040]** Further test blind spots · REPORTED
No test runs a single tick of any background worker (`healthCheckWorker`/`reconcileWorker` 0.0% on
all ten), so `CheckHealth`, the `AuthFailing → Healthy` recovery path, the 1h hold and the 24h
delay are unexercised. **Zero storage-failure tests exist** — VERIFIED. `upstream_timeout` is still
asserted only in its own unit test, and no fake can produce a client-side timeout (the fakes have no
timeout, expiry-simulation or rate-limit-window knobs, though `design.md:404` claims all three).
Two invisible gap channels: `ProbeLeavesNoUpstreamResidue` is registered only when
`ExpectsHardRevoke` (6 of 10) with no printed reason, and `error-taxonomy`'s forced-status cases
skip on AWS/GCP (4 of 5 on OCI) while the matrix prints `run` — those being exactly the clouds with
the fragile classifiers of A16. Two skip reasons are about the harness, not the cloud
(AGENTS.md rule 3). `pkg/plugintest` itself has **0.0% coverage**; `pkg/credenvelope/fakes` 61.7%;
GCP's production IAM/SA-key client and AWS's `iam_minter_client.go` are **0%** — the rotation
key-management paths `free-account-viability.md` calls "least-verified" are in fact unverified.
Rotation-concurrent-with-issue is untested on all six rotation clouds; OVH's e2e sets
`Upstream: nil`, so every upstream assertion in its run is a silent no-op.

## Verified clean

Recorded because a clean result is also information, and because it bounds the blast radius.

- **No credential material in logs** — all 166 non-test `Logger()` sites read; every value is an
  identifier, name, count, duration, status or error; no `%+v`/`%#v` in non-test code. Caveat by
  design: `"error", err` carries upstream bodies to the operator log, so server logs must be
  classified as holding upstream cloud diagnostics.
- **Metric labels are bounded and secret-free** — `{cloud, role, worker, minter_set, cred_id, state}`;
  `cred_id` is the minter ID, never secret material; no lease id, `req.ID` or error string is a label.
- **Storage minimisation** — the only persisted secrets are `Minter.Token` and OCI's
  `slot.TokenValue`, both unavoidable; all ten `internal_data` payloads and tracking entries hold
  only IDs and timestamps; no read endpoint returns a minter secret.
- **No storage-key traversal** — anchored `GenericNameRegex` admits no `/`; `ValidateSetName` pins
  set names; the `metrics/entity/<id>` path escapes all three segments.
- **Crypto and signing are sound** — AWS uses the SDK's `v4.Signer` with a correct payload hash;
  EdgeGrid HMAC-SHA256 is correct (key derivation, UTC timestamp, 16 bytes of `crypto/rand` nonce,
  body cap); GCP JWT is RS256 over SHA-256 with `rand.Reader`. No `math/rand`, SHA-1, MD5 or reused
  nonce. **FIPS: no non-approved primitive**; the one residual is no minimum RSA key size on
  operator-supplied SA JSON.
- **TLS** — zero `InsecureSkipVerify`, zero `tls.Config` in non-test code.
- **No committed credentials, including in history** — only AWS's own published example key; all
  fixtures added in one commit with one revision each, so there is no earlier unredacted revision.
- **Reconciler fail-closed guards, where they apply** — aborts with zero deletes on a `KnownIDs`
  error; `MaxDeletesPerPass` is not caller-tunable and fails closed at 0; `dry_run` deletes nothing.
- **`rotateSweepMu` discipline** — held across the whole rotate body, same mutex fronts the sweep,
  ordering consistent in all six; two concurrent rotates cannot both mint. No AB-BA path and no
  reentrant `RLock` deadlock anywhere.
- **Role TTL bounds** are honoured and stronger than documented, on both `default_ttl` and
  `max_ttl`. **Renewability** matches the documented four exactly, with no
  `resp.Secret.Renewable =` assignment anywhere.
- **`verify_minter_capability` defaults ON on both axes** (`*bool` + nil-receiver, and
  `Default: true` in all ten schemas).
- **The error-code vocabulary is fully reachable** — no second `consent_required`.
- **Mechanical enforcement works**: `TestEveryPluginIsRegistered`, `ValidateHarness`, the printed
  matrix, the `forbidigo` ban, zero `//nolint`, zero `context.Background()` in tests, exactly ten
  commented production roots. The failure mode is one level down — the matrix counts categories,
  not reachable assertions.
- **KI-002 is genuinely fixed** for its stated cause; the fallback log labels the residual harm
  honestly.
- **Licensing** — all 61 linked modules are Apache-2.0, MIT, BSD-3, ISC or MPL-2.0; nothing
  vendored, no generated code, no pseudo-versions, all 12 `replace` directives local.

## Points requiring a decision before implementation

These are not technical judgement calls; each has a materially different outcome depending on the
answer, and three of them are constrained by things outside this repo.

**D1 — Metrics (A12).** Can a plugin process emit metrics an operator can scrape at all? The SDK
carries no sink and the plugin is a separate process. Options: (a) find and use an OpenBao
mechanism if one exists; (b) have the plugin serve its own Prometheus endpoint (needs a listener
inside a secrets-engine process — likely unacceptable); (c) accept that metrics cannot work in this
deployment, **delete every metric claim from the docs**, and move the operator-facing signals to
structured logs, which do work. This decides A6, A23, A26, A27 and the DO-rotation design.

**D2 — Endpoint overrides (A3).** The test architecture points these fields at
`http://127.0.0.1:PORT`, so "validate `https://` + allowlist" would break every HTTP-fake plugin
test and the e2e layer. Options: (a) allow `http://` only for loopback, `https://` otherwise, with a
host allowlist for known clouds; (b) move the override behind a build tag so "for testing" becomes
true, and have tests use the tagged build; (c) keep the field but require an explicit
`allow_insecure_endpoint=true` alongside it. (a) is the least disruptive; (b) is the most honest.

**D3 — Exoscale/Vultr reclamation (A5).** The fail-closed age guard and reclaimability are in direct
tension on clouds whose APIs return no creation timestamp. Options: (a) allow an explicit
`confirmation_hold=0` on the *manual* endpoint only, restoring KI-004's workaround and accepting
that a human took responsibility; (b) reclaim from local tracking only, which cannot see the
entities that actually leak; (c) accept the leak, correct KI-004 and `ttl-semantics.md`, and
document the manual cleanup procedure.

**D4 — OCI (A15).** (a) Implement OCI request signing — substantial, and unverifiable without a
tenancy; (b) mark the plugin **experimental/not supported** in the three status documents and the
README table, keeping it as the phased-rotation reference; (c) remove it. Note (b) leaves phased
rotation with no working cloud, which matters because it is one of the two headline strategies.

**D5 — Owner-tag scheme (A19, and it interacts with A1).** Fixing multi-mount collision means
putting mount/cluster identity into the tag, which changes the naming scheme — so credentials
issued under the old scheme are unrecognised by the new filter, and that is a migration on live
upstream state. Options: (a) new scheme + a documented one-time reconcile-with-old-prefix
migration; (b) match either scheme for one release, then drop the old; (c) leave the scheme and
document the constraint loudly (one mount per cloud account).

**D6 — AWS narrowing fields (A22).** Implement `policy_arns`/`inline_policy` as specified (real
least-privilege value, moderate work) or delete them from the spec. I lean implement, because the
alternative is telling operators to create one IAM role per privilege level.

Everything else I will proceed on without asking, in the order given under "Critical" then "High",
with a stated assumption where one is needed.
